I am building a high-concurrency ticket booking system.

I want you to implement the architecture described below EXACTLY as the core design.

Do NOT replace this architecture with a completely different seat-booking architecture. If you identify a critical correctness issue, explain it first and then make the smallest necessary change while preserving the fundamental architecture.

IMPORTANT:
- Assume Redis is always available.
- Do NOT implement Redis crash recovery.
- Do NOT implement durable PostgreSQL seat-hold records as a backup for Redis.
- Do NOT introduce a PostgreSQL HELD seat state.
- The temporary HELD state exists in Redis.
- PostgreSQL is responsible for durable/permanent booking state.
- Redis is responsible for the high-frequency real-time seat inventory and temporary reservation layer.

==================================================
1. HIGH-LEVEL ARCHITECTURE
==================================================

The system has these major components:

1. Frontend
2. Backend/API servers
3. Waiting Room
4. Redis
5. PostgreSQL
6. Payment Gateway

Responsibilities:

FRONTEND:
- Display event page
- Display seat map
- Display seat colors
- Display selection timer
- Display payment timer
- Display payment status
- Display booking/ticket information

WAITING ROOM:
- Only used when an event has extremely high traffic
- Controls how many users enter the actual booking system
- Provides backpressure/traffic shaping
- Must NOT be mandatory for normal traffic

REDIS:
- Real-time operational seat inventory
- Temporary seat holds
- TTL/expiration
- Atomic seat acquisition
- High-concurrency coordination
- Fast seat-map reads
- Prevent users from acquiring seats that are already temporarily held or permanently booked
- Stores BOOKED state as well so stale clients do not attempt to acquire already-booked seats

POSTGRESQL:
- Durable source of truth for permanent booking
- Users
- Events
- Venues
- Seats
- Orders
- Payments
- Tickets
- Final seat state
- ACID transaction for final booking

PAYMENT GATEWAY:
- Handles actual payment
- Backend must never keep a PostgreSQL transaction open while waiting for payment

2. IMPORTANT STATE MODEL
==================================================

Redis maintains the real-time operational state of each seat.

Redis states:

AVAILABLE
HELD:{holdId}
FINALIZING:{holdId}
BOOKED

Example:

seat:3:A10 -> AVAILABLE

or:

seat:3:A10 -> HELD:H123

or:

seat:3:A10 -> FINALIZING:H123

or:

seat:3:A10 -> BOOKED


PostgreSQL maintains the durable seat state.

PostgreSQL seat states:

AVAILABLE
BOOKED

DO NOT create:

status = HELD

in the PostgreSQL seats table.

Temporary HELD state exists only in Redis.

Therefore:

Redis:
AVAILABLE -> HELD -> AVAILABLE
                   \
                    -> FINALIZING -> BOOKED

PostgreSQL:
AVAILABLE -> BOOKED

==================================================
7. USER SELECTS A10
==================================================

User A clicks A10.

Frontend may immediately display:

A10 -> BLUE

But this is only optimistic UI.

Frontend sends:

POST /booking-sessions/S123/seats/A10


Backend must attempt to acquire the seat in Redis atomically.

Use:

SET seat:3:A10 HOLD:H123 NX EX 600

Meaning:

seat:3:A10
    value = HOLD:H123
    NX = only create if key/state allows acquisition
    EX 600 = 10-minute TTL

If the seat is AVAILABLE:

Redis:

A10 -> HELD:H123
TTL = 600 seconds

Return success.

If the seat is already:

HELD
FINALIZING
BOOKED

then reject the request.

Example:

User B tries to acquire A10 while:

A10 -> HELD:H123

Redis atomic acquisition fails.

Return:

A10 is unavailable.

DO NOT perform a PostgreSQL query for every seat selection.

Redis is the high-frequency acquisition layer.

==================================================
17. POSTGRESQL FINAL BOOKING
==================================================

Now perform a SHORT PostgreSQL transaction.

Start:

BEGIN;

Lock the relevant seat rows:

SELECT *
FROM seats
WHERE event_id = 3
AND seat_id IN ('A10', 'A11')
FOR UPDATE;


Verify that the seats are still AVAILABLE.

Then:

UPDATE seats
SET status = 'BOOKED',
    version = version + 1
WHERE event_id = 3
AND seat_id IN ('A10', 'A11')
AND status = 'AVAILABLE';


Then create the order:

INSERT INTO orders (...);


Then create the booking-seat/order-item records:

INSERT INTO booking_seats (...);


Then create tickets:

INSERT INTO tickets (...);


Then update payment/order state:

UPDATE orders
SET status = 'CONFIRMED'
WHERE order_id = 'O123';


Then:

COMMIT;


IMPORTANT:

The transaction must remain short.

Never call the payment gateway while the transaction is open.

==================================================
24. PAYMENT IDEMPOTENCY
==================================================

Payment and booking APIs MUST be idempotent.

Handle:

- User clicks Pay twice
- Payment gateway sends duplicate webhook
- Backend receives duplicate payment response
- Network timeout after payment succeeded
- User retries payment
- Payment callback arrives multiple times

Example:

order_id = O123

If O123 is already:

CONFIRMED

then another success callback must NOT:

- create another order
- create another ticket
- book the seats again

The operation should simply return the existing successful booking.

Use an idempotency key/order ID/payment ID and appropriate unique database constraints.

26. REDIS DATA MODEL
==================================================

Design Redis carefully.

The logical state should be:

seat:{eventId}:{seatId}

Possible values:

AVAILABLE
HELD:{holdId}
FINALIZING:{holdId}
BOOKED

For temporary holds:

HELD:{holdId}

must have a TTL.

Example:

seat:3:A10 -> HELD:H123
TTL = 600 seconds


For permanent BOOKED state:

seat:3:A10 -> BOOKED

No temporary TTL should remove BOOKED state.

For seat map reads, use an efficient Redis data structure such as:

- Redis Hash
- Redis String keys
- Sets
- Another appropriate structure

Do NOT perform thousands of individual Redis calls if the entire seat map can be retrieved efficiently in one/batched operation.

Explain your chosen Redis data structure and why.


==================================================
27. REDIS ATOMICITY
==================================================

Seat acquisition MUST be atomic.

Do NOT implement:

GET seat
if available
SET seat

because this has a race condition.

Instead use:

SET NX

or a Lua script / Redis transaction where necessary.

For multiple seats, prefer an atomic Lua script or another safe Redis mechanism so:

ALL requested seats are acquired

OR

NONE are acquired.

==================================================

The frontend seat map is only a snapshot.

Backend checks Redis.

Reject.

Similarly, after A permanently books A10:

Redis:

B may still visually see AVAILABLE.

When B clicks:

Redis says BOOKED.

Reject.

The backend must always validate seat acquisition.

33. FINAL ARCHITECTURE PRINCIPLE
==================================================

The most important design principle is:

Redis handles:

- High-frequency seat operations
- Current operational seat state
- Temporary holds
- TTL
- Atomic acquisition
- Fast seat availability checks

PostgreSQL handles:

- Durable booking state
- Orders
- Payments
- Tickets
- Final seat ownership
- ACID transaction

Waiting Room handles:

- Traffic spikes
- Backpressure
- Admission control

Frontend handles:

- UI
- Timers
- Seat colors
- Real-time updates

The frontend is never trusted for correctness.
